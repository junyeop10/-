description: 코드베이스에 변경 사항을 커밋(Commit)할 때 **반드시** 준수해야 할 팀 커밋 메시지 규칙 정의.
---

### 1. 언어 및 문체 (팀 공통)
- **한국어 작성 권장**
- **간결한 명사형**으로 작성 (예: `~추가`, `~수정`, `~정리`)

### 2. 커밋 메시지 구조
기본은 제목 1줄로 충분합니다. 필요 시 본문을 추가합니다.

- **기본 포맷:** `<type>: <내용>`
- **(선택) 본문:** 왜 바꿨는지 1~3줄로 추가
  - 한 줄 최대 72자 권장
  - 제목과 본문 사이 빈 줄 1개

### 3. 타입 (Type) 지정 규칙
제목의 `<type>`은 다음 중 하나를 **반드시** 선택하여 소문자로 작성할 것.
- **feat:** 새로운 기능 추가
- **fix:** 버그 수정
- **docs:** 문서 수정 (README, 주석 등)
- **style:** 코드 포맷팅, 세미콜론 누락 수정 등 코드의 로직에 영향을 주지 않는 변경
- **refactor:** 코드 리팩토링 (기능 추가나 버그 수정이 없는 코드 변경)
- **test:** 테스트 코드 추가 및 수정
- **chore:** 빌드 업무 수정, 패키지 매니저 환경설정 등 (프로덕션 코드 변경 없음)

### 4. 제목 (Subject) 작성 규칙
- **길이 제한:** 제목은 50자 이내 권장
- **과거형 금지:** `~했다` ❌ → `~수정`, `~추가`, `~정리` ✅
- **마침표 금지:** 제목 끝에 `.` 금지
- **(선택) 스코프:** 팀에서 합의된 경우에만 사용 (예: `feat(backend): ...`)

### 5. 본문 (Body) 작성 규칙 (선택 사항이나 권장)
- **작성 기준:** How(구현 상세)보다 **What/Why** 위주로 작성
- **문단 구분:** 필요 시만

### 6. 꼬리말 (Footer) 작성 규칙 (선택 사항)
- **이슈 연결:** 관련된 이슈 트래커 ID를 닫거나 참조할 때 사용할 것.
  - (예시) `Resolves: #12`
  - (예시) `See also: #34, #56`
- **파괴적 변경(Breaking Changes) 명시:** 하위 호환성을 깨뜨리는 변경 사항이 있다면 `BREAKING CHANGE:` 로 시작하여 변경 내용을 명시할 것.

---

### 예시

- `feat: Stage3 로컬 LLM 폴백 추가`
- `fix: 업로드 후 WebSocket 진행 이벤트 누락 수정`
- `docs: 컨벤션 문서 구조 정리`
