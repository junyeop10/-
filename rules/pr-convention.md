## 1. PR을 왜 작성하나

- **작업 의도 공유:** 왜 변경했는지 팀이 빠르게 파악하기 위함
- **리뷰 품질 향상:** 변경 범위·검증 방법을 미리 제공하기 위함
- **이력 추적:** 나중에 문제 발생 시 변경 이유를 되짚기 위함

## 2. 기본 원칙

- PR은 **작고 명확한 단위**로 나눌 것
- 제목/본문은 **한국어로 간결하게** 작성할 것
- 이슈가 있다면 PR 본문에서 연결할 것 (`Resolves: #번호`)
- 커밋/이슈 규칙은 각각 `commit-convention.md`, `issue-building.md`를 따를 것

## 3. PR 제목 규칙

- 형식: `<type>: <한 줄 요약>`
- 예시:
  - `feat: Stage3 로컬 LLM 폴백 로직 추가`
  - `fix: 업로드 후 진행 상태 이벤트 누락 수정`
  - `docs: 팀 컨벤션 문서 구조 정리`

## 4. PR 본문 필수 항목

아래 4개는 반드시 포함할 것.

### 배경
- 왜 이 변경이 필요한지

### 변경 내용
- 무엇을 바꿨는지 핵심 목록

### 테스트
- 로컬/수동 테스트 방법 및 결과

### 영향 범위
- 어떤 모듈·화면·API에 영향이 있는지

## 5. PR 본문 템플릿

```md
## 배경
- 

## 변경 내용
- 

## 테스트
- [ ] 로컬 실행 확인
- [ ] 주요 시나리오 확인
- [ ] 예외/실패 케이스 확인 (해당 시)

## 영향 범위
- 

## 체크리스트
- [ ] 관련 이슈 연결 (`Resolves: #번호`)
- [ ] 커밋 메시지 규칙 준수
- [ ] 민감정보(.env, 키) 미포함
```

## 6. 좋은 PR 기준 (권장)

- 리뷰어가 10분 내 이해 가능한 분량
- 변경 이유가 본문에 분명히 적혀 있음
- 테스트 방법을 그대로 따라하면 재현 가능함
