# Claude API 파이프라인 연동 — 담당 기여 정리

## 역할

이 프로젝트에서 Stage 5(카테고리 분류)의 Claude API 연동과, 이를 파이프라인 전체(`main.py`)에 붙이는 백엔드 통합을 맡았다. 팀은 문서 파일을 업로드하면 룰 기반 매칭 → 임베딩 → 의미 신호 계산을 거치고, 그래도 애매하게 남는 파일을 Claude API로 최종 분류하는 구조로 파이프라인을 설계했다. 그중 Claude 호출·프롬프트 구성·응답 처리·파이프라인 연결이 내 담당 영역이다.

## 실제로 구현한 것

### Claude API 호출 (`pipeline/stage5_claude.py`)

- `classify_with_claude()` / `classify_with_claude_rag()` 두 함수로 1차·2차 분류를 각각 처리한다. `anthropic.AsyncAnthropic`으로 비동기 호출하고, `asyncio.Semaphore`로 동시 호출 수(`MAX_CONCURRENT_LLM`, 기본 5)를 제한해 대량 업로드 시 API 과호출을 막는다.
- 실패하면 1회 재시도하고, 그래도 실패하면 `분류불가` 상태로 반환해 검토 큐로 넘어간다.

### 프롬프트 구성 (`pipeline/stage5_common.py`)

- 시스템 프롬프트에 8개 카테고리 설명과 출력 JSON 스키마를 고정하고, 유저 프롬프트는 파일명·확장자·키워드 힌트·본문 앞/중간/뒤 텍스트로 구성한다.
- 본문은 초반/중간/후반 각 1500자씩만 잘라 넣는다(입력 예산 총 4500자). 문서 전체를 매번 보내면 비용과 응답 시간이 늘어나기 때문에, 분류 판단에 필요한 부분만 표본으로 추출하는 방식을 택했다.
- 2차(RAG) 프롬프트는 1차에서 저신뢰·기타·실패로 걸린 파일에만 유사 카테고리 힌트를 추가로 붙여 다시 묻는다. 모든 파일에 2차 호출을 걸지 않고 필요한 경우에만 트리거해 호출 횟수를 줄였다.

### 응답 파싱

- 모델 응답에서 정규식으로 `{...}` JSON 블록을 추출해 `json.loads`로 파싱한다. 카테고리가 8개 목록에 없으면 "기타"로 강제하고, confidence는 0.0~1.0으로 클램핑한다. 파싱 실패 시 `None`을 반환해 재시도·실패 처리로 넘어간다.

### 에러 처리

- 처음에는 모든 실패를 "API 오류" 한 줄로 뭉뚱그렸는데, 이후 커밋(`937985a`)에서 `AuthenticationError`(API 키 오류), `RateLimitError`(요청 한도 초과), 크레딧 부족을 구분해 반환하도록 고쳤다. 실패 사유가 구체적이어야 검토 큐에 쌓인 파일을 어떻게 처리할지(키 재설정인지, 잠시 후 재시도인지) 판단할 수 있어서다.

### 파이프라인 연결 (`main.py`, `db/cache.py`)

- `run_pipeline()`에서 pre_stage → 텍스트 추출/OCR → 룰 매칭 → 임베딩 → `stage5_classify.run()` → 확정/검토 큐 순서로 각 단계를 연결하고, WebSocket으로 진행 상태를 브로드캐스트한다.
- xxhash로 파일 해시를 계산해 SQLite에 캐시해두고, 동일 파일이 재업로드되면 Claude를 다시 부르지 않고 캐시된 분류 결과를 바로 반환한다.
- 사용자가 `/confirm`으로 분류를 수정하면 그 기록을 저장해두고, 다음 분류 때 임베딩 유사도가 일정 기준 이상이면 Claude 호출 전에 바로 확정한다(`stage5_classify.py`의 1단계).

### 테스트 도구

- `test_claude.py`로 서버 없이 로컬 파일·폴더만 넣어 Claude 1차 분류를 바로 확인할 수 있게 했고, `--dry-run` 옵션은 API를 호출하지 않고 프롬프트만 미리 보여준다(비용 없이 프롬프트 점검용).
- 팀원들이 전체 서버 환경을 설치하지 않고도 Claude 부분만 테스트할 수 있도록 `claude-llm-test/` 패키지(테스트 매뉴얼, zip 패키징 스크립트)를 만들었다.

## 왜 이렇게 설계했나

- 문서 전체를 매 요청마다 API로 보내면 비용과 응답 시간이 늘어난다고 판단해서, 본문을 앞/중간/뒤 표본(4500자)만 잘라 보내고, 룰·임베딩으로 이미 확실한 파일은 애초에 Claude까지 안 가도록 앞단에서 걸러지는 구조로 설계했다.
- 캐시(xxhash)와 임베딩 유사도 선분류도 같은 이유다. 이미 본 파일이거나 과거 사용자 수정과 비슷하면 Claude를 다시 부르지 않는다.
- 2차(RAG) 호출도 모든 파일이 아니라 1차에서 애매했던 파일에만 걸었다. 이 경계는 `stage5_classify.py`의 `_needs_rag_retry()`에 있다 (confidence 0.6 미만이거나 카테고리가 "기타"이거나 실패한 경우).

## 팀이 만든 부분 

같은 파이프라인 안에서 아래 단계는 다른 팀원이 담당했다. Claude API 앞단에서 이 결과들을 입력으로 받아 쓰긴 하지만, 구현은 각자 담당 브랜치에서 이뤄졌다.

- 텍스트 추출(Stage 1) — 김준엽
- OCR, 파일명 룰 기반 분류(Stage 2, 3) — 정건우
- SBERT 임베딩, HDBSCAN 클러스터링(Stage 4, 6) — 천승원
- 검토 큐 UI(Stage 7) — 정윤서
- 학습(가중치 조정 등)과 GUI/CLI 프로토타입(`app.py`, `app_gui.py`)은 별도 레거시 코드베이스로, 다른 팀원이 만들었다.

## 수치

코드 자체에서 정확도·처리 시간을 측정하는 로직은 없어서, 아래 수치는 직접 검증한 값이 아니라 팀 발표자료(2026년 6월) 기준이다.
